# Campus room server

Run `npm run serve:online`, then open `http://127.0.0.1:8931/` in two browser windows. Create a room in one window and enter its six-digit code in the other. Two connected human players are required to start. The other pupils are AI decoys and do not count as network players.

The same process serves `dist/` and the authenticated `/api/` routes. `HOST` defaults to `0.0.0.0`; `PORT` defaults to `8931`. Another device on the same network can use the computer's LAN IP and port, subject to its firewall. Restart the process after changing the server or rules modules. There are no install-time dependencies.

The server runs the classroom simulation, validates commands, reserves seats, selects the teacher, advances shared items and doors, and distributes personalized state through authenticated fetch/SSE streams. Client submissions cannot set positions, points, inventory or another player's identity. Private drawer contents and metadata identifying mischievous students are removed from teacher snapshots. Each room owns its layout and collision context. Room tokens are random bearer tokens and are never included in other players' responses. A disconnected player has sixty seconds to reconnect using the same in-memory token; a page reload currently requires a new lobby join. Rooms are transient and do not survive a process restart.

Role and appearance preferences can be changed in the lobby. The host can select one of the eight floors. Starting selects one teacher among volunteers, or among all connected humans if there are no volunteers. That teacher stays in the locked office for the full thirty-second countdown. A teacher disconnecting permanently ends the round; a host leaving the lobby transfers host status to another member. After a result the host can call `await round.rematch()` to return everyone to the corridor, retaining the room code and choosing a new desk layout. Roles are selected again on the next start. The local pause menu stops that player's controls; it does not pause the other players.

Mouse look is applied immediately in the client, with a server acknowledgement sequence. Other characters are rendered through a short interpolation buffer. Position, collision, item usage and points remain server-controlled. The HTTP command interval is forty milliseconds and snapshots are sent fifteen times per second. This is appropriate for the current classroom game; it is not a competitive high-tick shooter transport.

On reconnect the client sends `since`, its last applied state sequence. The server replays eligible events still in the room's 100-event buffer, with the same recipient/role privacy filters; the client discards duplicate event sequences. The latest authoritative state is always sent even if older events have expired. A stream with no valid state for ten seconds is aborted and retried after 1.5 seconds. Disconnection clears pending input and unacknowledged local look; commands are refused until the stream reconnects, so old clicks are not replayed. An abandoned create/join session that never opens a stream enters the disconnect grace period after fifteen seconds. A failed room closes its streams and reports a terminal room error without stopping the HTTP service.

API replies and SSE state are validated before use. HTML from a static host, proxy or incorrect endpoint produces a readable server-address error rather than `Unexpected token '<'`; it is not treated as a working room service. Malformed JSON envelopes, command parameters and voice signals are rejected before forwarding. To run these recovery checks together with the response-validation tests, use `node --test qa/server-recovery56.test.mjs qa/network-response53.test.mjs` (requires a temporary loopback listener).

Voice is optional WebRTC audio. It requests microphone permission only when the player presses the microphone control or M, and uses room-scoped authenticated signaling. Muting disables audio tracks; leaving stops them and closes peer connections. Voice needs HTTPS or localhost. A plain HTTP LAN address can run the game but browsers normally block its microphone. The included configuration uses STUN and direct peer-to-peer audio. Some mobile or restrictive networks need a TURN relay, which is not configured. No audio is recorded by this Node server. Voice signaling is covered by tests; actual microphone playback between two physical devices still needs a listening test.

If an audio track ends because the microphone disappears or permission is revoked, the voice control switches off and releases the unusable stream and peers. Pressing M again requests a new stream. Old track events and asynchronous negotiation cannot close or alter the replacement connection.

`npm run test:online` starts an ephemeral local HTTP server and verifies independent peers, token rejection, origin checks, host-only start, role assignment, movement, privacy filtering, reconnect, room-scoped voice signaling, seat conflicts, item completion, timed doors and separate room layouts. It also checks public held props without private inventory, office chair exclusivity across roles, shared drawer movement, banana peel flight/landing/stun, garlic burps, bubble growth/attachment, and teacher ink/flash/stun state. Score feedback is personalized; global effects remain visible to the other clients. The HTTP test requires permission to listen on a loopback port.

GitHub Pages can serve the client files but cannot run this Node process. No public persistent server deployment or paid hosting purchase is included. To make internet rooms available, deploy this folder plus `dist/` to an actual Node host and serve it behind HTTPS, with proxy buffering disabled for `/api/events`. The easiest origin setup is serving the game and API from this same process. HTTP loopback preview origins (`localhost`, `127.0.0.1`, `[::1]`) are allowed on development ports. Other separate client origins must be explicitly added using `ALLOWED_ORIGINS=https://example.com`; there is no wildcard CORS setting. The current process is one instance with in-memory rooms; use a single instance or sticky room routing until shared persistence is implemented.

For this repository's GitHub Pages client, launch the deployed server from the repository root with the exact client origin allowed:

```sh
HOST=0.0.0.0 PORT=8931 ALLOWED_ORIGINS=https://nornttyy.github.io node server/server.js
```

Terminate HTTPS at the host or reverse proxy and forward both `/api/` and the event stream to that process. Then enter the public HTTPS server origin (for example `https://rooms.example.com`, not the GitHub Pages URL or `/api` path) in the game's multiplayer server field. The example domain is a placeholder, not an existing deployed service. The health URL at that origin, `/api/health`, must return JSON with `ok: true` and `protocol: 1`; an HTML hosting page is not a room backend. Other players must use that same backend and room code. A public HTTPS page cannot use a plain HTTP remote backend, and `127.0.0.1` always points to each player's own computer. Publishing the GitHub branches alone does not perform any of this server deployment.
